# Аудит загрузки: «Ученики → карточка ученика → задание»

Дата: 26 октября 2026. Ветка: `arena/31ddd53f-english-lms`.

## Краткий ответ

Сайт тормозил не из‑за одного тяжёлого запроса, а из‑за нескольких перегрузок на всём пути преподавателя:

1. **`/teacher/students/`** делал `2N` дополнительных SQL‑запросов на группы учеников и рендерил **всех** учеников без пагинации.
2. **Карточка ученика** строила и отправляла полное дерево курса со всеми ответами и разборами тестов, хотя большая часть интерфейса скрыта. На тестовом курсе из 144 заданий HTML весил **682 КБ**.
3. **Динамический HTML вообще не сжимался**: WhiteNoise сжимал только статику, а `GZipMiddleware` отсутствовал. Браузер получал все 682 КБ без `Content-Encoding`.
4. **Каждый аудиоответ** создавал `<audio preload="metadata">`, поэтому браузер сразу делал отдельный приватный запрос на файл — по 9 SQL‑запросов на запрос и `no-store`. 20 вложений = 20 сетевых запросов и 180 SQL‑запросов только на метаданные.
5. **Декоративная сцена енота** перерисовывала canvas 60 раз/с на каждой странице, даже когда вкладка неактивна или сцена вне viewport.
6. Клик «Показать содержимое как видит ученик» по отдельному заданию выполнял общий `visibility_q()` со множеством вложенных подзапросов, хотя проверялось одно задание.

Сам HTMX‑запрос предпросмотра был относительно лёгким — ~18 мс на сервере; основная задержка ощущалась уже на входе в раздел и при открытии карточки ученика.

**Дополнительно по запросу пользователя** из карточки ученика удалены блоки «Последние 30 попыток» и «Навыки». Вместе с ними убраны 3 SQL‑запроса (один на список последних сдач и два на сводку навыков) и ~13 КБ HTML в регрессионном тесте на 25 заданий.

## Методика замеров

### Серверный стенд

- Django 5.2.18, Python 3.11, SQLite для воспроизводимого синтетического стенда. Production использует PostgreSQL, поэтому абсолютные времена SQL будут другими, но количество запросов, размер HTML и сетевые метрики справедливы для обеих БД.
- Синтетический курс: 6 классов × 2 главы × 3 темы × 4 задания = **144 задания**, 40 учеников, 480 сдач, 108 вопросов, 432 варианта, 720 ответов по пунктам.
- Замеры `django.test.Client` с `CaptureQueriesContext`, 5 повторов, медиана после прогрева. Замерялись wall time, число SQL, суммарная длина SQL, размер HTML, gzip‑размер и число DOM‑узлов.
- Для production‑подобной статики: `collectstatic` с `CompressedManifestStaticFilesStorage`, Gunicorn + WhiteNoise, hashed static files.

### Браузерный стенд

- Headless Chromium 153 через Playwright/Playwright Core.
- 1280×800, три сценария:
  - `local` — без throttle;
  - `slow` — 1.6 Мбит/с, задержка 150 мс, CPU 4×;
  - `slow_reduced` — то же + `prefers-reduced-motion: reduce`.
- Собирались TTFB, `load`, FCP, LCP, CLS, long tasks/TBT, `transferSize`, `encodedBodySize`, `decodedBodySize`, количество ресурсов и DOM‑узлов, частота `requestAnimationFrame`.
- Ограничение: в этом headless‑билде CDP‑метрика `TaskDuration` возвращала 0, поэтому вместо общего CPU% использовались количество rAF‑вызовов и время JS внутри них. Long tasks >50 мс и CLS в обоих прогонах были 0.

1. **`lms/views_teacher.py`, `lms/templates/lms/teacher_students.html`** — список учеников постраничный (`LMS_PAGE_SIZE`), `prefetch_related("student_groups")`, статистика только по текущей странице. N+1 устранён.
2. **`lms/views_teacher.py`, `lms/templates/lms/teacher_student_detail.html`, новый partial** — ответы и разборы пунктов больше не рендерятся для всех заданий. Кнопка «Показать ответ и разбор» грузит HTMX‑фрагмент `/teacher/students/<id>/assignments/<id>/progress/`. Для работы без JS есть `?details=<id задания>`. Дополнительно удалены блоки «Последние 30 попыток» и «Навыки».
3. **`lms/curriculum.py`** — для карточки ученика (`sql_states=False`) шесть коррелированных `Subquery` заменены одним запросом последних сдач; каталог ученика сохранил прежний бюджет ≤8 SQL.
4. **`lms/audience.py`** — новая `assignment_is_visible_to()` проверяет видимость одного задания компактными `EXISTS` вместо полного `visibility_q()`. Покрыта тестами сравнения с `Assignment.objects.visible(user=...)`.
5. **`core/settings.py`** — добавлен `django.middleware.gzip.GZipMiddleware`; в `docs/DEPLOYMENT.md` описано, что ingress не должен сжимать ответ повторно и должен иметь rate limit.

7. **Шаблоны аудио** — все `preload="metadata"` заменены на `preload="none"`.
8. **Тесты** — добавлены регрессии на query budget, пагинацию, gzip, ленивую загрузку ответов, HTMX‑фрагмент, проверку аудитории и отсутствие metadata‑preload; обновлены тесты удалённых блоков. Полный набор: **775 тестов, OK** (`skipped=6`).
9. **Удаление второстепенных блоков** — вместе с «Последними 30 попытками» и «Навыками» убраны `_skill_summary()`, `SKILL_BANDS`, выборка последних сдач и связанные контекстные ключи. Это ещё минус 3 SQL‑запроса и ~13 КБ HTML на карточку.

## Рекомендации для production

1. **Проверить сжатие на ingress.** GZipMiddleware уже сжимает HTML; Nginx/платформа не должны сжимать ответ повторно. Сохраните общий rate limit как меру против BREACH.
2. **Снять `EXPLAIN (ANALYZE, BUFFERS)` в PostgreSQL** для оставшегося ~10 КБ `visibility_q()` на реальных объёмах. Если он попадёт в `pg_stat_statements` как топ, следующий шаг — материализованная карта аудитории или денормализованные `visible_to` связи.
3. **Не кэшировать приватный HTML** и ответы `/preview/` без проверки прав. Текущие `private, no-store` для файлов корректны.
4. **Разгрузить файлы.** Для большого числа аудио используйте `X-Accel-Redirect`/sendfile или подписанные URL объектного хранилища, чтобы Gunicorn не держал worker на каждой выдаче.
5. **Настроить worker’ы под нагрузку.** `WEB_CONCURRENCY=3` sync‑воркера мало, если одновременно открывают карточки с вложениями. Рассмотрите `gthread` и мониторинг queue time.
6. **Добавить RUM‑метрики** (PerformanceObserver для LCP/INP/CLS) и бюджет скорости в CI: число SQL, размер сжатого HTML, transfer size. Часть бюджетов уже зафиксирована в `lms/tests/test_queries.py`.
7. **Разделить frontend‑бандлы** при следующем изменении UI: `lms.js` и `components.css` уже составляют ~56 КБ gzip из ~94 КБ общей статики.
8. **Для курсов на сотни заданий** можно пойти дальше и вынести весь блок действий задания (кнопки предпросмотра и разбора) в один HTMX‑фрагмент по кнопке «Открыть задание». Сейчас компактная строка задания всё ещё занимает ~2.8 КБ разметки; после сжатия это ~10–20 КБ на страницу, но на слабых устройствах DOM остаётся ощутимым.

# Второй проход: «Классы», переход на уровень задания и кнопки разбора

Дата: 26 октября 2026. Ветка: `arena/c33e09e4-english-lms`. Продолжение аудита выше:
промерены все вкладки преподавателя и ученика (34 экрана), отдельно — «Классы» и
переход на уровень задания, плюс две кнопки в карточке ученика
(«Показать ответ и разбор», «Показать содержимое как увидит ученик»).

## Краткий ответ

Тормозило не одно место, а шесть разных перегрузок:

1. **Проверка доступа к одному заданию стоила как фильтр всего каталога.**
   `assignment_is_visible_to()` строил `visibility_q(user)` — по два-три подзапроса
   на каждую группу ученика на каждом из четырёх уровней цепочки. Django собирал
   этот SQL в Python (28 КБ текста), а база его разбирала. На микро-стенде
   (200 заданий, 8 групп) одна проверка стоила **21.4 мс**; на классе из 1 группы —
   5.6 мс. Цена росла с числом групп, а не с числом заданий: страница задания,
   каждый клик «Проверить», каждая выдача приватного файла платили её заново.
2. **Доска темы носила в себе все формы быстрых правок.** Каждое задание темы
   получало `AssignmentQuickForm` плюс форму каждого пункта автопроверки:
   **13 021 Б HTML и ~9 SQL на одно задание** (после правки — 5 436 Б). Тема из
   24 заданий — около 310 КБ разметки только на формы и 200+ запросов. Это и был
   медленный «переход на уровень задания».
3. **Счётчик «Проверка» в навигации пересчитывался в каждом HTMX-фрагменте и писал
   сессию.** `console_context()` читал очередь целиком (`latest_attempts()` с
   коррелированным `NOT EXISTS` по всем сдачам), клал результат в `request.session`,
   и каждый ответ — даже фрагмент на 0.3 КБ — завершался `UPDATE django_session`.
   Параллельные запросы одного пользователя сериализовались на этой строке.
   Отсюда «иногда грузит очень долго»: медиана клика 3–4 мс, а отдельный клик —
   14–57 мс (см. таблицу большого класса ниже).
4. **Карта курса считала аудиторию каждого задания**, хотя шаблон показывал бейджи
   только у класса, главы и темы: четыре prefetch'а правил на все 144 задания.
5. **Журнал оценок («Аналитика») отдавал всю матрицу сразу.** 40 учеников × 144
   задания = 5 760 клеток, **1 376 КБ HTML, 12 972 DOM-узла, 233 мс** — самая тяжёлая
   вкладка сайта. Плюс `gradebook()` заранее prefetch'ил 14 связей аудитории на все
   задания, собирая полноценные модели классов, глав, тем и учеников.
6. **Экран сроков резал список в Python.** `upcoming()` загружал и аннотировал все
   задания с дедлайнами курса, а показывал первые 100.

## Методика

- `docs/audit/perf_probe.py` — общий стенд: 6 классов × 2 главы × 3 темы × 4 задания
  (144 задания, 432 вопроса), 40 учеников, 320 сдач. Меряет wall time, число и «вес»

## До и после: большой класс (150 учеников, 12 групп, 4800 сдач)

То, на что жаловались пользователи, — кнопки в карточке ученика:

| экран | было | стало | SQL | SQL КБ |
|---|---:|---:|:---:|---:|
| HTMX: «Показать ответ и разбор» | 4.3 мс, **max 14.2** | 3.6 мс, **max 6.3** | 10 → **6** | 5.6 → 4.4 |
| HTMX: «Показать содержимое как увидит ученик» | 18.7 мс, **max 57.3** | **12.7 мс**, max 17.4 | 10 → 11 | 11.5 → 10.5 |
| Карточка ученика (страница) | 59.4 мс | **52.0 мс** | 11 | 28.2 |
| Консоль после фрагментов | 70.8 мс | **53.6 мс** | 33 → **26** | 22.1 → 18.8 |

Главное — не медиана, а `max`: в «до» отдельный клик фрагмента занимал 42–57 мс
вместо 4–18 мс, потому что в этот запрос попадали пересчёт очереди и запись сессии.

## Что исправлено в коде

1. **`lms/audience.py` — `AudienceRules`.** Один UNION-запрос по строкам аудитории
   (назначения и исключения групп и учеников на всех уровнях цепочки) вместо десятков
   подзапросов; проверка «открыт ли уровень» считается один раз на набор, а не на
   задание. `assignment_is_visible_to()` теперь `AudienceRules(user, [a]).allows(a)`:
   2–3 запроса, цена не зависит от числа групп ученика и от числа проверенных заданий
   (микро-стенд: 21.4 → 5.5 мс на 8 группах, 4.1–5.1 мс на одной).
   Добавлены `visible_assignment()`, `visible_assignment_or_404()`, `filter_visible()`
   для пообъектных и списочных проверок, `effective_ids_bulk()` — матрица
   «задание → получатели» связующими таблицами, и `ASSIGNMENT_OWN_PREFETCH` /
   `TOPIC_CHAIN_PREFETCH` для prefetch'ов правил.
2. **Все пообъектные проверки student-пути переведены на `AudienceRules`**:
   `assignment_detail`, `_item_action`, `quiz_finish`, `quiz_retake`, `save_draft`,
   сессия тренажёра, карточки темы и `_resolve_private_file` (`lms/views.py`,
   `lms/views_student.py`). Список/каталог по-прежнему фильтруется одним
   `visibility_q()` в SQL — там это правильно.
3. **Счётчик очереди убран из сессии** (`lms/context_processors.py`,
   `lms/curriculum.py`): `cached_queue_counts()` держит значение 60 с в кэше процесса,
   `put_cached_queue_counts()` обновляет его со экрана очереди, а для HTMX/XMLHttpRequest
   (`is_fragment_request`) счётчик не считается вовсе. Фрагмент больше не пишет
   `django_session` — проверено тестом на отсутствие `Set-Cookie`.
4. **Доска темы: форма быстрых правок по требованию.** Новый partial
   `lms/templates/lms/parts/assignment_quick_editor.html` и адрес
   `GET /teacher/curriculum/assignments/<pk>/quick-editor/`. Доска отдаёт строки
   заданий без форм; `<summary>` тянет форму через `hx-get` с `hx-trigger="click once"`,
   кнопка «Редактировать» и «Развернуть все задания» догружают форму тем же вызовом из
   JS. Глубокая ссылка `?edit=<pk>` и возврат на доску с ошибками сохранения рендерят
   форму сразу — поведение без JavaScript сохранено (в подсказке есть ссылка на полный
   редактор). Разметка на задание: 13.0 → 5.4 КБ, форма на тему вместо форм на все задания.
5. **Карта курса: `course_tree(..., assignment_audience=False)`.** Правила самих
   заданий не подгружаются, если их никто не показывает; `audience.accumulate()`
   для уровня без своих правил возвращает копию родительского словаря вместо
   пробега по получателям; `audience.details()` показывает не больше
   `AUDIENCE_TOOLTIP_LIMIT = 8` имён («и ещё N»), иначе тултип класса на 60 учеников
   весил больше самой строки.
6. **Журнал оценок: страницы учеников и компактные клетки.** `gradebook_students()` +
   `Paginator` по `LMS_PAGE_SIZE`, `gradebook(..., students=page.object_list)` считает
   только строки страницы; ссылка разбора, подпись статуса и цвет плашки готовятся в
   `gradebook()` вместо `{% url %}`/фильтров в шаблоне; пустая и «без оценки» клетки
   рисуются CSS (`.grade-col.is-pending`, `.is-not-assigned`) вместо `<span>` с `title`
   на каждую; легенда вынесена в `<caption>`. Выгрузка XLSX осталась полной матрицы.
7. **Экран сроков режет список в базе** (`lms/views_student.py`, `UPCOMING_LIMIT`),
   а не в Python после аннотаций.
8. **Тесты.** `lms/tests/test_queries.py` — бюджеты: доска темы без инлайн-форм и с
   плоским числом запросов, карта курса не зависит от числа заданий, HTMX-фрагменты не
   считают очередь (`lms.curriculum.queue_counts` подменяется счётчиком вызовов),
   журнал постраничный, + gzip. `lms/tests/test_audience.py` — `effective_ids_bulk()`
   обязан совпасть с пообъектным расчётом на Fixture с наследованием, исключениями и
   персональными назначениями. `lms/tests/test_browser.py` — форма догружается кликом,
   повторное открытие не дёргает сеть. Обновлены тесты, которые закрепляли инлайн-форму
   на каждом задании (`test_board.py`, `test_paste_uploads.py`, `test_topic_editing.py`).
   Полный набор: **781 тест, OK** (`skipped=6` — опциональные браузерные).

## Что осталось дорогим

1. **`visibility_q()` для всего каталога** — по-прежнему ~100 OR-условий и 28 КБ SQL на
   страницу ученика (главная 49–53 мс, курс 60 мс). Правильный следующий шаг —
   считать множества id на уровень одним набором `values_list` и оставлять в SQL только
   `IN (…)`: семантику «исключить группу B, оставить A» это сохраняет, но менять нужно
   с A/B-проверкой на всех тестах доступа.
2. **413 КБ HTML карты курса** (21.6 КБ gzip) — сам список заданий на классе. Дальше
   только ленивые главы или разрез по классам; сервер при этом стоит 67 мс, из них
   ~20 мс — SQL, остальное — отрисовка шаблона.
3. **374 КБ карточки ученика**: 11 SQL, но 214 кнопок и 2.5 КБ разметки на задание.
   Поможет единый HTMX-фрагмент на строку задания (кнопки + прогресс), как в аудите выше.
4. **51 SQL и 116 КБ у полного редактора задания**: 22 запроса на полные строки
   `auth_user` и 20 на `lms_group` — это `own_rules()` на четырёх уровнях цепочки;
   prefetch закрывает половину. Ещё 6 запросов — `ensure_skill_catalog()`, который
   `get_or_create`-ит шесть навыков на каждый вызов: его стоит кэшировать, но
   осторожно (в тестах id навыков меняются от базы к базе).
5. **Разбор сдачи (16 мс) и очередь (21 мс)** остались с прежним бюджетом — там
   всё в одном `latest_attempts()`; на больших архивах стоит смотреть индексы в PG.

## Как воспроизвести

```bash
python docs/audit/perf_probe.py --scale 6x2x3x4 --students 40 --reps 9 \
    --json docs/audit/perf_results_after.json
python docs/audit/class_scale_probe.py          # большой класс: кнопки и очередь
```

Для A/B достаточно второго worktree на базовой ревизии:

```bash
git worktree add /tmp/lms_before 78e825d
cd /tmp/lms_before && python /path/to/.venv/bin/python docs/audit/class_scale_probe.py
```
