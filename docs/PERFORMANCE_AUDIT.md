# Аудит загрузки: «Ученики → карточка ученика → задание»

Дата: 26 октября 2026. Ветка: `arena/31ddd53f-english-lms`.

## Краткий ответ

Сайт тормозил не из‑за одного тяжёлого запроса, а из‑за нескольких перегрузок на всём пути преподавателя:

1. **`/teacher/students/`** делал `2N` дополнительных SQL‑запросов на группы учеников и рендерил **всех** учеников без пагинации.
2. **Карточка ученика** строила и отправляла полное дерево курса со всеми ответами и разборами тестов, хотя большая часть интерфейса скрыта. На тестовом курсе из 144 заданий HTML весил **682 КБ**.
3. **Динамический HTML вообще не сжимался**: WhiteNoise сжимал только статику, а `GZipMiddleware` отсутствовал. Браузер получал все 682 КБ без `Content-Encoding`.
4. **Каждый аудиоответ** создавал `<audio preload="metadata">`, поэтому браузер сразу делал отдельный приватный запрос на файл — по 9 SQL‑запросов на запрос и `no-store`. 20 вложений = 20 сетевых запросов и 180 SQL‑запросов только на метаданные.
5. **Декоративная сцена енота** перерисовывала canvas 60 раз/с на каждой странице, даже когда вкладка неактивна или сцена вне viewport.
6. Клик «Показать содержимое как видит ученик» по отдельному заданию выполнял общий `visibility_q()` со множеством вложенных подзапросов, хотя проверялось одно задание.

Сам HTMX‑запрос предпросмотра был относительно лёгким — ~18 мс на сервере; основная задержка ощущалась уже на входе в раздел и при открытии карточки ученика.

**Дополнительно по запросу пользователя** из карточки ученика удалены блоки «Последние 30 попыток» и «Навыки». Вместе с ними убраны 3 SQL‑запроса (один на список последних сдач и два на сводку навыков) и ~13 КБ HTML в регрессионном тесте на 25 заданий.

## Методика замеров

### Серверный стенд

- Django 5.2.18, Python 3.11, SQLite для воспроизводимого синтетического стенда. Production использует PostgreSQL, поэтому абсолютные времена SQL будут другими, но количество запросов, размер HTML и сетевые метрики справедливы для обеих БД.
- Синтетический курс: 6 классов × 2 главы × 3 темы × 4 задания = **144 задания**, 40 учеников, 480 сдач, 108 вопросов, 432 варианта, 720 ответов по пунктам.
- Замеры `django.test.Client` с `CaptureQueriesContext`, 5 повторов, медиана после прогрева. Замерялись wall time, число SQL, суммарная длина SQL, размер HTML, gzip‑размер и число DOM‑узлов.
- Для production‑подобной статики: `collectstatic` с `CompressedManifestStaticFilesStorage`, Gunicorn + WhiteNoise, hashed static files.

### Браузерный стенд

- Headless Chromium 153 через Playwright/Playwright Core.
- 1280×800, три сценария:
  - `local` — без throttle;
  - `slow` — 1.6 Мбит/с, задержка 150 мс, CPU 4×;
  - `slow_reduced` — то же + `prefers-reduced-motion: reduce`.
- Собирались TTFB, `load`, FCP, LCP, CLS, long tasks/TBT, `transferSize`, `encodedBodySize`, `decodedBodySize`, количество ресурсов и DOM‑узлов, частота `requestAnimationFrame`.
- Ограничение: в этом headless‑билде CDP‑метрика `TaskDuration` возвращала 0, поэтому вместо общего CPU% использовались количество rAF‑вызовов и время JS внутри них. Long tasks >50 мс и CLS в обоих прогонах были 0.

## Вложения и аудио

Специальный замер с 20 голосовыми ответами в одном задании:

| Метрика | Было | Стало |
|---|---:|---:|
| `<audio>` в исходном HTML карточки | 20 | 0 |
| `<audio preload="metadata">` | 20 | 0 |
| Запросов `/preview/...` сразу после загрузки | 20 | 0 |
| Запросов `/preview/...` после открытия разбора | — | 0 |
| `<audio>` после открытия разбора | 20 | 20, но `preload="none"` |

Каждый такой запрос в teacher‑режиме выполнял 9 SQL‑запросов (сессия/пользователь/роль + 6 проверок таблиц файлов), занимал ~4–5 мс после прогрева и возвращал `Cache-Control: private, no-store`. Для 20 вложений это ~180 SQL‑запросов и ~80–100 мс чистого времени worker’ов. При `WEB_CONCURRENCY=3` такие запросы легко занимают все sync‑воркеры.

После исправления приватные файлы не загружаются автоматически: разбор ответов грузится по кнопке, а все `<audio>` используют `preload="none"`. Метаданные/аудио запрашиваются только когда преподаватель нажал play.

## Что исправлено в коде

1. **`lms/views_teacher.py`, `lms/templates/lms/teacher_students.html`** — список учеников постраничный (`LMS_PAGE_SIZE`), `prefetch_related("student_groups")`, статистика только по текущей странице. N+1 устранён.
2. **`lms/views_teacher.py`, `lms/templates/lms/teacher_student_detail.html`, новый partial** — ответы и разборы пунктов больше не рендерятся для всех заданий. Кнопка «Показать ответ и разбор» грузит HTMX‑фрагмент `/teacher/students/<id>/assignments/<id>/progress/`. Для работы без JS есть `?details=<id задания>`. Дополнительно удалены блоки «Последние 30 попыток» и «Навыки».
3. **`lms/curriculum.py`** — для карточки ученика (`sql_states=False`) шесть коррелированных `Subquery` заменены одним запросом последних сдач; каталог ученика сохранил прежний бюджет ≤8 SQL.
4. **`lms/audience.py`** — новая `assignment_is_visible_to()` проверяет видимость одного задания компактными `EXISTS` вместо полного `visibility_q()`. Покрыта тестами сравнения с `Assignment.objects.visible(user=...)`.
5. **`core/settings.py`** — добавлен `django.middleware.gzip.GZipMiddleware`; в `docs/DEPLOYMENT.md` описано, что ingress не должен сжимать ответ повторно и должен иметь rate limit.
6. **`lms/static/lms/js/raccoon_scene.js`** — сцена ограничена ~30 кадрами/с, останавливается при `document.hidden`, вне viewport через `IntersectionObserver` и при `prefers-reduced-motion: reduce`.
7. **Шаблоны аудио** — все `preload="metadata"` заменены на `preload="none"`.
8. **Тесты** — добавлены регрессии на query budget, пагинацию, gzip, ленивую загрузку ответов, HTMX‑фрагмент, проверку аудитории и отсутствие metadata‑preload; обновлены тесты удалённых блоков. Полный набор: **775 тестов, OK** (`skipped=6`).
9. **Удаление второстепенных блоков** — вместе с «Последними 30 попытками» и «Навыками» убраны `_skill_summary()`, `SKILL_BANDS`, выборка последних сдач и связанные контекстные ключи. Это ещё минус 3 SQL‑запроса и ~13 КБ HTML на карточку.

## Рекомендации для production

1. **Проверить сжатие на ingress.** GZipMiddleware уже сжимает HTML; Nginx/платформа не должны сжимать ответ повторно. Сохраните общий rate limit как меру против BREACH.
2. **Снять `EXPLAIN (ANALYZE, BUFFERS)` в PostgreSQL** для оставшегося ~10 КБ `visibility_q()` на реальных объёмах. Если он попадёт в `pg_stat_statements` как топ, следующий шаг — материализованная карта аудитории или денормализованные `visible_to` связи.
3. **Не кэшировать приватный HTML** и ответы `/preview/` без проверки прав. Текущие `private, no-store` для файлов корректны.
4. **Разгрузить файлы.** Для большого числа аудио используйте `X-Accel-Redirect`/sendfile или подписанные URL объектного хранилища, чтобы Gunicorn не держал worker на каждой выдаче.
5. **Настроить worker’ы под нагрузку.** `WEB_CONCURRENCY=3` sync‑воркера мало, если одновременно открывают карточки с вложениями. Рассмотрите `gthread` и мониторинг queue time.
6. **Добавить RUM‑метрики** (PerformanceObserver для LCP/INP/CLS) и бюджет скорости в CI: число SQL, размер сжатого HTML, transfer size. Часть бюджетов уже зафиксирована в `lms/tests/test_queries.py`.
7. **Разделить frontend‑бандлы** при следующем изменении UI: `lms.js` и `components.css` уже составляют ~56 КБ gzip из ~94 КБ общей статики.
8. **Для курсов на сотни заданий** можно пойти дальше и вынести весь блок действий задания (кнопки предпросмотра и разбора) в один HTMX‑фрагмент по кнопке «Открыть задание». Сейчас компактная строка задания всё ещё занимает ~2.8 КБ разметки; после сжатия это ~10–20 КБ на страницу, но на слабых устройствах DOM остаётся ощутимым.
