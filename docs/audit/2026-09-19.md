## Заключение

**Проект — работоспособный каркас MVP, но в текущем состоянии не готов к промышленной эксплуатации с реальными работами и персональными данными учеников.** Рекомендуется отложить публичный запуск до устранения замечаний P1 и проверки инфраструктурных требований.

Архитектура небольшого Django-монолита соответствует масштабу задачи; переписывать приложение или вводить микросервисы не требуется. Основные проблемы — не выбор технологий, а безопасность конфигурации и файлов, целостность процесса проверки работ, отсутствие тестов и эксплуатационных гарантий.

Наиболее существенные подтверждённые результаты:

- сохраняется **1001 балл при максимуме задания 100**;
- создание пользователя через админку с заполненным inline-профилем заканчивается `IntegrityError`;
- при `DEBUG=True` ответ ученика можно скачать **без авторизации**, зная URL; при `DEBUG=False` приложение само не обслуживает этот URL;
- пересдача заменяет ответ, но сохраняет старую оценку и первоначальную дату отправки;
- преподаватель может оценить уже изменённый ответ, который не видел; редактирование комментария проверки через админку переводит работу с доработки в проверенные;
- обязательный файл можно удалить и всё равно получить статус «Сдана»;
- штатный тестовый набор содержит **0 тестов**.

Выделены **20 групп замечаний: 8 P1, 11 P2 и 1 P3**. Это приоритеты устранения, а не баллы CVSS. Часть замечаний относится к процессу разработки или зависит от инфраструктуры; они не объявляются доказанными атаками на действующий сервер.

## 3. Что реализовано правильно

1. Основные страницы требуют входа; ученику недоступна операция преподавательской проверки.
2. HTML-страница ученика получает только его собственную сдачу, фильтруя по `request.user`.
3. Неактивные задание, тема и блок закрыты для ученика; прямой переход возвращает 404.
4. CSRF middleware включён, POST-формы содержат токены. Проверены HTTP 403 без токена и HTTP 405 для GET-выхода.
5. Текст ответов, условий и комментариев экранируется шаблонизатором. Выполнение внедрённого HTML/JS в проверенных текстовых полях не воспроизвелось.
6. Поиск использует Django ORM; в исходниках нет ручной конкатенации SQL или пользовательских `eval`/`exec`.
7. Расширения загрузок ограничены, имена генерируются через UUID. `.exe` отвергается. Это полезные меры, хотя их недостаточно для полной защиты файлов.
8. Уникальность сдачи на пару ученик–задание и slug темы внутри блока закреплена ограничениями БД.
9. Миграции соответствуют моделям и применяются на SQLite. WhiteNoise корректно обслуживает собранную статику.
10. Стандартный LoginView отклоняет внешний `next`; отрицательная оценка отвергается. Простое создание ученика через Admin без изменения inline-профиля работает.

Утечка файлов ниже относится к отдельному каналу `/media/` и не означает, что фильтрация HTML-страниц ученика отсутствует.

## 5. Подробно: замечания P1

### A01. Небезопасная конфигурация по умолчанию

**Код:** [core/settings.py:19–24](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/core/settings.py#L19-L24), [142–151](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/core/settings.py#L142-L151), [.env.example:1–3](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/.env.example#L1-L3).

- При отсутствии переменных используется публичный fallback `SECRET_KEY`, а `DEBUG=True`.
- Даже после `DJANGO_DEBUG=False` HTTPS redirect и флаги Secure для session/CSRF cookies по умолчанию выключены, HSTS равен нулю.
- `SECURE_PROXY_SSL_HEADER` доверяет заголовку прокси; корректность его удаления/установки внешним прокси в репозитории не подтверждена.

**Последствие:** приложение допускает запуск с недопустимыми для production настройками. Публичный ключ компрометирует секретность подписей; debug-ответы раскрывают диагностическую информацию. Риски HTTP/cookies зависят также от внешней HTTPS-конфигурации. Сам по себе fallback-ключ здесь не доказывает произвольный вход в чужую серверную сессию.

**Исправление:** production-конфигурация должна прекращать запуск без случайного секрета, явных hosts и настроек БД; выключать debug по умолчанию. Включить Secure cookies, обеспечить HTTPS redirect в приложении или на доверенном прокси. HSTS включать после проверки всех нужных HTTPS-доменов, без слепого включения preload/includeSubDomains. Документировать все поддерживаемые переменные.

**Приёмка:** некорректное production-окружение не запускается; `check --deploy --fail-level WARNING` проходит в утверждённой конфигурации; cookies и редиректы проверены через настоящий прокси.

### A02. Нет защищённой выдачи файлов

**Код:** [core/urls.py:11–12](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/core/urls.py#L11-L12), [core/settings.py:118–128](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/core/settings.py#L118-L128), [assignment_detail.html:38–43, 68–73](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/templates/lms/assignment_detail.html#L38-L73).

Имеются две стороны одной проблемы:

1. С `DEBUG=True` маршрут `static(... MEDIA_ROOT)` отдаёт файлы без проверки владельца и роли. Для известного URL ответа получен HTTP 200 как анонимным клиентом, так и другим учеником.
2. С `DEBUG=False` маршрут исчезает. Тот же существующий файл возвращает 404 даже владельцу. WhiteNoise обслуживает статику, но не решает выдачу `MEDIA_ROOT`.

UUID делает URL трудным для угадывания, но не заменяет авторизацию: известная или переданная ссылка продолжает предоставлять доступ. Публичная раздача `/media/` внешним Nginx устранит 404, но оставит проблему конфиденциальности.

**Исправление:** скачивание через endpoint с проверкой пользователя и объекта; далее защищённый `FileResponse`, внутренний `X-Accel-Redirect` либо приватное объектное хранилище с короткоживущими подписанными URL. Для материалов задания также определить политику доступа. Не публиковать ответы учеников как общедоступную статику.

**Приёмка:** владелец и уполномоченный преподаватель скачивают файл при `DEBUG=False`; анонимный пользователь и чужой ученик не получают содержимое даже по известному URL. Проверить также заменённые и удалённые файлы.

**Воспроизведение:** проверки `06`, `07`; наблюдения `media_acl`, `production_media`.

### A03. Можно сохранить оценку выше всех заявленных ограничений

**Код:** [lms/forms.py:81–85, 109–113](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/forms.py#L81-L113), [lms/views.py:174–187](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/views.py#L174-L187), [lms/models.py:246–249](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/models.py#L246-L249), [lms/admin.py:116–122](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/admin.py#L116-L122).

Присваивание `self.fields["grade"].max_value` после создания `IntegerField` не добавляет `MaxValueValidator`. В наблюдаемом списке валидаторов остаётся только `MinValueValidator`. Обычный `save()` модели также не запускает её `full_clean()`.

**Доказательство:** форма признала допустимым `grade=1001` для задания с `max_points=100`; POST вернул 302, в БД сохранилось 1001. Через форму Django Admin отдельно принят балл 101 для максимума 100: там проверяется общий лимит модели, но не лимит конкретного задания.

**Исправление:** создавать поле с нужным валидатором либо явно валидировать верхнюю границу в `clean_grade()`. Продублировать инвариант в общем сервисе записи/модельной валидации, которую реально вызывают все пути записи, включая Admin. Определить поведение при уменьшении максимума уже оценённого задания.

**Приёмка:** тесты на `-1`, `0`, `max_points`, `max_points + 1`, `1001` и пустое значение; недопустимая оценка никогда не сохраняется ни одним интерфейсом.

**Воспроизведение:** `01`, `24`, `26`.

### A04. Сигнал создания профиля конфликтует с Admin inline

**Код:** [lms/models.py:66–74](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/models.py#L66-L74), [lms/admin.py:8–16](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/admin.py#L8-L16).

При сохранении нового `User` сигнал уже создаёт `Profile`. Затем изменённая inline-форма Admin пытается создать второй профиль с тем же `user_id`.

**Доказательство:** заполнение роли преподавателя/Telegram/комментария при создании пользователя приводит к `UNIQUE constraint failed: lms_profile.user_id`. Создание пользователя откатывается. Контрольный сценарий обычного ученика с неизменённым inline работает; ошибка не относится безусловно ко всем созданиям пользователей.

**Исправление:** выбрать единственный механизм создания профиля. Простой вариант — не показывать профиль на странице добавления пользователя и редактировать его после создания. **Приёмка:** через Admin создаются ученик и преподаватель, с пустым и заполненным профилем; на каждого пользователя остаётся ровно один профиль.

### A05. Пересдача нарушает связь «ответ — время — оценка»

**Код:** [lms/views.py:78–104](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/views.py#L78-L104), [154–190](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/views.py#L154-L190), [lms/models.py:209–228](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/models.py#L209-L228), [assignment_detail.html:77–90](https://github.com/vasgrishin-a11y/english_lms/blob/d6699680b0a3cf43488d9a232c33335d3a308ac5/lms/templates/lms/assignment_detail.html#L77-L90).

Один `Submission` перезаписывается при каждой отправке. Истории попыток и версии ответа нет.

Подтверждены три последствия:

- После новой отправки статус становится `submitted`, но предыдущие `Feedback.grade/comment` остаются и показываются рядом с новым ответом без привязки к старой попытке.

**Исправление:** ввести неизменяемые попытки/версии сдач, привязать проверку к попытке; либо как минимум хранить номер версии, время последней отправки и явно отделять старый feedback. При сохранении проверки сверять ожидаемую версию и возвращать конфликт, если ответ изменился. Одной блокировки БД в момент POST недостаточно для обнаружения устаревшей страницы преподавателя.

**Приёмка:** нельзя незаметно оценить другую версию; видна история/принадлежность комментариев; просрочка вычисляется для нужной попытки; старые оценки не выдаются за оценку нового ответа.

## 7. Архитектурные и продуктовые ограничения — не автоматически ошибки

Эти пункты следует согласовать с владельцем продукта, а не исправлять исходя из непредоставленных требований:

- **Единое пространство обучения.** Каждый ученик видит все активные задания; каждый преподаватель — все сдачи. Нет групп, enrollment, владельцев курса или связей «преподаватель–ученики». Второй преподаватель действительно открыл чужую сдачу в проверке `17`. Для единой школы/одного преподавателя это может быть нормой; для независимых клиентов или классов требуется объектная изоляция.
- **Роль и админ-доступ различаются.** `Profile.role=teacher` даёт интерфейс проверки, но не даёт автоматически `is_staff` и административные permissions. С другой стороны, новый staff автоматически получает роль teacher. Нужна понятная матрица прав; не следует решать выдачу преподавательского доступа массовой раздачей superuser.
- **Нет личного управления паролем ученика.** Маршруты самостоятельной смены/восстановления пароля отсутствуют. Описать безопасный onboarding и восстановление доступа.
- **Очередь — не журнал успеваемости.** Проверенные работы исключены из списка, отдельного архива и прогресса ученика нет. Статусы NEW/IN_REVIEW практически не участвуют в обычном пользовательском процессе.
- **Дедлайн сейчас информационный.** Поздние ответы разрешены. Нужна согласованная политика попыток, доработок и срока, а не произвольное добавление запрета.
- **Удаления каскадные.** Удаление учебной иерархии может удалить связанные сдачи/проверки. Определить правила архивирования и удержания данных.
- **Модель пользователя частично жёстко связана со стандартным `User`.** FK используют `AUTH_USER_MODEL`, но сигнал и Admin импортируют конкретный `User`. Сейчас это работает; переход на custom user потребует согласованных изменений.

Рекомендуемое развитие архитектуры: оставить Django, вынести операции сдачи/проверки в небольшой сервисный слой с явными инвариантами, ввести историю попыток и проверки прав для файлов, оптимизировать ORM и закрепить поведение тестами.

## 9. Воспроизведение и доказательства

### Изолированные сценарии

Скрипт проверяет **исходный коммит**, а не исправленную версию. Экспортируйте исходное дерево, не меняя рабочую ветку:

```bash
mkdir -p /tmp/english-lms-baseline
git archive d6699680b0a3cf43488d9a232c33335d3a308ac5 | tar -x -C /tmp/english-lms-baseline
```

В отдельном виртуальном окружении, с установленными зависимостями исходного дерева:

```bash
python3 -m venv /tmp/english-lms-audit-venv
. /tmp/english-lms-audit-venv/bin/activate
python -m pip install -r requirements.txt
AUDIT_REPO=/tmp/english-lms-baseline python docs/audit/reproduce.py
```

Сценарий до инициализации Django принудительно подменяет подключение на SQLite в памяти, использует временный каталог файлов и случайный тестовый секрет. Он не запускает миграции в реальной БД. Упрощённый MD5 hasher применяется только в этих временных тестах для скорости и не меняет настройки приложения.

Для сохранения наблюдений и синтетических HTML-страниц вне репозитория:

```bash
AUDIT_ARTIFACTS=/tmp/english-lms-audit-results \
  AUDIT_REPO=/tmp/english-lms-baseline python docs/audit/reproduce.py
```

Для точного повторения учитывать версии из раздела 2: широкие требования со временем разрешатся иначе. После исправления дефектов соответствующие characterization assertions должны перестать проходить — их следует заменить регрессионными ожиданиями правильного поведения.

### Остальные команды аудита

Выполнять с отдельной БД; не направлять `migrate` на production ради повторения аудита:

```bash
export DATABASE_URL=sqlite:////tmp/english-lms-audit-checks.sqlite3
export DJANGO_MEDIA_ROOT=/tmp/english-lms-audit-media

python manage.py check
python manage.py check --deploy
DJANGO_DEBUG=False python manage.py check --deploy
python manage.py makemigrations --check --dry-run
python manage.py migrate --noinput
python manage.py test --verbosity 2
python -m pip check

# Инструменты аудита устанавливаются отдельно от runtime-зависимостей.
pip-audit -r requirements.txt --progress-spinner off
bandit -r core lms manage.py
ruff check --isolated --select E4,E7,E9,F core lms manage.py
detect-secrets scan
sh -n docker-entrypoint.sh
```

`collectstatic` в аудите запускался с временным `STATIC_ROOT`, затем Django Test Client проверил production-mode страницы и статику. Браузеру передавались только синтетические страницы из сценария `30`; выполнен `axe.run(document)` на desktop и измерение overflow при ширине 320 px.

[results.json](results.json) содержит версии, результаты команд, все 32 наблюдения, dependency audit и браузерные измерения. Это доказательства конкретного локального исследования, не сертификат безопасности и не утверждение о текущем состоянии внешнего production-развёртывания.
