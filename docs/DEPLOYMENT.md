# Развёртывание и эксплуатация

## Требования и ограничения

Python 3.12 / Django 5.2, PostgreSQL 15+ (CI: 16), постоянное приватное файловое хранилище и HTTPS reverse proxy. SQLite и `core.test_settings` не предназначены для production. Один учебный коллектив на развёртывание; для разных клиентов нужны отдельные экземпляры.

Без случайного `DJANGO_SECRET_KEY` (не менее 50 символов), явных hosts, PostgreSQL и абсолютного `DJANGO_MEDIA_ROOT` production-профиль не запускается. `DEBUG=False` по умолчанию. HTTPS redirect и Secure cookies включены по умолчанию.

Скопируйте `.env.production.example` в **не отслеживаемый Git** `.env.production` либо внесите значения в secret manager платформы. `secrets.token_urlsafe(64)` подходит для нового ключа. Не записывайте реальные пароли в README, логи CI или PR. При смене ключа учитывайте завершение старых сессий.

Для внешней PostgreSQL используйте `DATABASE_URL` с URL-encoded реквизитами и `sslmode=require`/`verify-full` согласно требованиям провайдера. Вариант PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE поддерживается; пробелы и спецсимволы реквизитов корректно экранируются.

## HTTPS и доверенные заголовки

- Gunicorn слушает `0.0.0.0:$PORT` (8000 по умолчанию). Внешнему миру доступен **только HTTPS ingress**, не сам backend.
- `DJANGO_TRUST_PROXY_SSL_HEADER=True` задаётся только если ingress **перезаписывает**, а не дополняет `X-Forwarded-Proto`. Иначе клиент может подделать защищённую схему.
- Для axes по умолчанию используется REMOTE_ADDR. Если нужен реальный IP за прокси, задайте `DJANGO_TRUSTED_PROXY_IPS` точными адресами/CIDR прямых доверенных peers и перезаписывайте `X-Real-IP`. Не доверяйте произвольному X-Forwarded-For и не используйте `0.0.0.0/0`.
- HSTS по умолчанию — 3600 секунд. После проверки HTTPS можно увеличить. **includeSubDomains/preload не включаются автоматически:** это решение владельца домена после проверки всех поддоменов. Только предупреждения W005/W021 по этим двум опциям намеренно исключены из deployment gate; остальные предупреждения должны блокировать выпуск.
- Ограничьте тело HTTP-запроса также на ingress, например `client_max_body_size 21m` для прикладного лимита 20 MiB; настройте таймауты медленной загрузки, общий rate limit и оповещения. Лимит приложения не заменяет сетевую защиту.

Схематичный location для Nginx внутри HTTPS server block:

```nginx
location / {
    client_max_body_size 21m;
    client_body_timeout 30s;
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For "";
    proxy_read_timeout 120s;
}
```

Сертификат, HTTP→HTTPS redirect и сеть доверенных peers настраиваются отдельно под ваш домен/платформу. При контейнерном bridge фактический REMOTE_ADDR может быть адресом gateway, а не `127.0.0.1` — проверьте его перед заданием trusted peers. **Не добавляйте `alias` для `/files/` или `/media/`.** WhiteNoise обслуживает только статические assets.

## Docker / Compose

`Dockerfile` закрепляет Python image digest, устанавливает runtime по хешам, собирает статику на build и запускает приложение как UID/GID **10001:10001**. Постоянный media volume должен быть доступен этому пользователю. Файлы имеют права 0600, каталоги загрузок — 0700; публичная статика отдельно имеет 0644/0755.

Пример single-host deployment:

1. Заполнить `.env.production`, добавить `POSTGRES_PASSWORD` для локальной БД Compose. Это отдельный секрет, не Django SECRET_KEY. Для Compose `DATABASE_URL` переопределяется на PGHOST-параметры внутреннего сервиса `db`; пароль с символами также поддерживается.
2. Настроить host/ingress TLS и trusted proxy headers. Укажите публичный hostname и при необходимости loopback hosts для локальных smoke-проб.
3. Выполнить:

```bash
docker compose --env-file .env.production build
docker compose --env-file .env.production up -d db
docker compose --env-file .env.production run --rm web python manage.py migrate --noinput
docker compose --env-file .env.production run --rm web python manage.py check --deploy --fail-level WARNING
# Предпочтительно интерактивное создание администратора:
docker compose --env-file .env.production run --rm web python manage.py createsuperuser
docker compose --env-file .env.production up -d web
```

Compose хранит БД и media в двух именованных volumes; порт БД наружу не публикуется, web опубликован только на loopback host для reverse proxy. Никогда не используйте `docker compose down -v` для обычного redeploy: это удаляет данные.

Если платформе (включая Amvera) удобнее build по Dockerfile без Compose, настройте внешнюю PostgreSQL и **постоянный mount** по `DJANGO_MEDIA_ROOT`. Само значение переменной и mkdir не обеспечивают персистентность. Убедитесь в правах UID 10001. При переносе старого media проверьте владельца и права также у вложенных каталогов/файлов, а не только у корня mount. Для нескольких реплик нужен общий приватный media volume; локальные независимые файловые системы не подходят.

## ИИ-помощник на площадке

Помощник работает и без модели: без `LMS_AI_LOCAL=1` материал разбирается офлайн-эвристиками,
поэтому развёртывание не зависит от внешнего сервиса. Чтобы включить разбор моделью, поставьте
рядом с приложением **Ollama** (или запустите LM Studio на рабочей машине) и задайте
`LMS_AI_PROVIDER`, `LMS_AI_LOCAL=1`, `LMS_AI_MODEL`. Сравнение моделей, требования к железу и
установка — [docs/AI_PROVIDERS.md](AI_PROVIDERS.md).

Практические требования:

- **Память под модель.** Модель уровня 7–8B занимает ~8 ГБ видеопамяти или оперативной памяти.
  Если на площадке столько нет, выбирайте модель поменьше (`gemma3:4b`) или держите Ollama на
  отдельной машине и укажите её адрес в `LMS_AI_ENDPOINT`.
- **Адрес модели.** По умолчанию помощник ходит на `http://localhost:11434/v1`. Если Ollama
  запущена в другом контейнере или на другом хосте, укажите `LMS_AI_ENDPOINT` и, например,
  `LMS_AI_MODEL=qwen3-vl:8b`. Ключ для локального сервера не нужен — он требуется только своему
  OpenAI-совместимому шлюзу с авторизацией.
- **Ollama на хосте, сайт в контейнере.** Внутри контейнера `localhost` — это сам контейнер, поэтому
  `http://localhost:11434/v1` до модели на хосте не дотянется, и помощник честно ответит «Нет связи
  с моделью». Compose уже прописывает для `web` алиас `host.docker.internal`; при сборке по Dockerfile
  без Compose берите адрес шлюза (`172.17.0.1` для сети bridge):
  `LMS_AI_ENDPOINT=http://host.docker.internal:11434/v1`.
- **Ресурсы и таймауты.** Разбор страницы на CPU занимает десятки секунд: держите
  `LMS_AI_TIMEOUT` (60 с по умолчанию, для локальной модели разумно 120 с) меньше, чем
  `proxy_read_timeout` у Nginx, иначе пользователь увидит таймаут прокси вместо ответа.
- **HTTPS не обязателен для localhost.** Локальный сервер модели общается по HTTP внутри
  контура: `LMS_AI_CA_BUNDLE` и `LMS_AI_VERIFY_SSL=0` нужны только для внутренних HTTPS-шлюзов,
  причём второй — лишь на время отладки: без проверки TLS можно перехватить ключ.
- **Проверка перед включением.** `python manage.py ai_check` показывает режим, провайдера,
  модель, адрес и вложения без сетевых запросов; `manage.py ai_check --live` делает ровно один
  пробный запрос и печатает понятную причину, если сервер модели не запущен.
- **Приватность.** Материалы преподавателя не покидают контур, а в журнал `lms.ai` пишутся
  только счётчики и коды ошибок: содержимое файлов и работ учеников не логируется.

## Миграции и администратор

По умолчанию entrypoint выполняет только `migrate --check`: сервис не стартует с неприменённой схемой. Миграции запускает **одна release job**, не каждая реплика. `DJANGO_RUN_MIGRATIONS=true` существует для контролируемого первого запуска/одной реплики и CI; не включайте его одновременно на всех экземплярах.

Для неинтерактивного bootstrap явно запустите `python manage.py bootstrap_admin` с DJANGO_SUPERUSER_USERNAME/PASSWORD и необязательным EMAIL через secret manager. Пароль валидируется. Существующий активный superuser остаётся неизменным; конфликт с обычной/отключённой учётной записью — ошибка, а не скрытое повышение прав. Удалите bootstrap-реквизиты после создания. Автовызов из entrypoint возможен только с `DJANGO_CREATE_SUPERUSER=true`.

## Обновление с коммита исходного аудита

1. Объявить maintenance window; остановить записи **всех** старых экземпляров.
2. Сделать согласованный backup PostgreSQL + media, проверить доступность предыдущего image digest и секретов. Для перехода со старой SQLite отдельно спланировать и проверить перенос данных в PostgreSQL на копии; миграция схемы не является переносом между СУБД.
3. Из новой сборки выполнить `python manage.py audit_legacy_data` против **старой схемы**. Команда только читает существующие поля. Оценки выше максимума/1000 требуют подтверждённой преподавателем коррекции. Не используйте автоматическое ограничение чисел до максимума: это незаметно меняет результаты обучения.
4. Разобрать предупреждения о feedback у непроверенных статусов. В старой версии ответ мог уже быть перезаписан, а feedback — остаться от прежнего содержания. Истинную старую версию восстановить программно нельзя; согласуйте такие записи вручную.
5. `migrate --plan`, затем `migrate --noinput` в одной release job. `0002` сохраняет ID, файлы, ответ и время; текущая запись становится попыткой 1, создаются снимки лимита/дедлайна и события из имеющихся данных. Некорректные границы оценок останавливают миграцию без молчаливого исправления.
6. Выполнить regression suite на staging, проверить преподавателя/ученика, скачивание при DEBUG=False, новую попытку и конфликт устаревшей проверки. Проверить auth для файла другого ученика и отсутствие public media alias.
7. Запустить новую версию и только затем открыть запись.

**Rollback:** `0002` намеренно необратима: возвращение прежней уникальности уничтожило бы историю нескольких попыток. Не выполняйте `migrate lms 0001` на новой рабочей базе. При необходимости вернуть старую версию — остановить запись и восстановить **согласованные предмиграционные backup БД+media вместе со старым image**. Учесть потерю новых записей согласно согласованному RPO. Предпочтительнее исправление вперёд, если новая запись уже открыта.

Старые `/media/…` ссылки становятся недействительными намеренно; новые авторизованные URL генерируются через `.url` из тех же сохранённых имён. Старые приватные ссылки из писем следует заменить, а не делать публичный redirect/alias.

## Резервирование и восстановление

Частоту, RPO/RTO, шифрование, регион хранения и срок хранения определяет владелец данных. Минимум: регулярный PostgreSQL dump/managed backup + копия private media, шифрование вне сервера приложения, контроль успешности, отдельная восстановительная среда.

Для согласованного простого backup на маленькой single-host установке:

1. Остановить все web/worker записи; не останавливать БД до dump.
2. `docker compose --env-file .env.production exec -T db pg_dump -U lms -d lms -Fc > <encrypted-or-protected-backup-path>`.
3. Скопировать volume private-media средствами платформы/backup agent с сохранением прав. **Не сохранять backup в публичную статику или Git**.
4. Зафиксировать image digest, время, версию схемы, checksum и защищённую ссылку на необходимые secrets.
5. Включить web после успешного завершения обеих частей.

Restore drill: восстановить dump через `pg_restore` в **отдельную пустую БД**, media — в отдельный volume с UID/GID 10001, запустить соответствующий image и миграции, проверить контрольные ответы, оценки, историю, скачивание и чужие права. Записать фактическое время восстановления. Не тестировать restore поверх production.

## Обслуживание и наблюдаемость

- `/health/live/` — процесс отвечает; `/health/ready/` — доступна схема БД и доступен для записи media-каталог. Ответ не содержит реквизитов. Эти два endpoint не требуют входа и исключены из HTTPS redirect для внутренних probes. Не трактуйте readiness как проверку свободного места или качества backup.
- Gunicorn пишет access/error logs в stdout/stderr; Django — ошибки, `lms.activity` — идентификаторы операций без текста ответа/пароля. `SubmissionEvent` хранит авторство и историю проверок в БД. Не предоставляйте журналы ученикам/публичному CDN.
- Подключить внешние alerts: 5xx, ошибки readiness, заполнение volume, доступность БД, всплески login lockout и ошибки backup. Срок хранения IP/login logs также должен быть определён владельцем данных.
- `python manage.py cleanup_orphan_files` — dry-run; после проверки `--delete`. По умолчанию удаляются только непривязанные файлы старше 24 часов в namespaces assignments/submissions. Старые попытки, пока есть записи, **не являются orphan**.
- `python manage.py axes_reset_logs 30` — очистка старых access logs согласно политике. Для снятия блокировки после проверки личности используйте `axes_reset_username USER`; это административная операция, не публичный endpoint.
- Архивировать задание через `is_active=False`, а не каскадным удалением: каталог с работами защищён от случайного удаления.
- `python manage.py purge_student USERNAME` сначала показывает dry-run. `--confirm-username USERNAME` необратимо удаляет обычного ученика и его учебные записи; общие файлы удаляются только когда исчезают все ссылки. Применять только по утверждённой политике удаления, с учётом backup retention; staff/teacher этим инструментом не удаляются.

## Финальная приёмка на платформе

- [ ] Проверены HTTPS, hosts, CSRF, secure cookies и отсутствие прямого публичного доступа к backend.
- [ ] Проверены действительные peers ingress; spoofed X-Real-IP/X-Forwarded-Proto не обходят политику.
- [ ] DB/media переживают настоящий redeploy; несколько реплик используют общее media.
- [ ] Выполнен restore drill, записаны RPO/RTO и ответственные за backup/alerts.
- [ ] Сняты bootstrap secrets, выполнены production checks, пройден CI.
- [ ] Пользователи и reviewers обучены работе с историей попыток и конфликтами 409.
- [ ] Для недоверенных документов утверждена политика антивируса/карантина; проверка формата не выдаётся за гарантию отсутствия вредоносного содержимого.

Эти проверки нельзя подтвердить только изменением файлов репозитория: они должны быть выполнены владельцем реального окружения перед запуском.
